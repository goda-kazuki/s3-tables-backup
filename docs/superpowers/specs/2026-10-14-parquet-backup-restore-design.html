Parquet 退避と特定の日への復元 設計

2026-10-14 / S3 Tables バックアップ記事の検証用 / 状態: レビュー待ち（未コミット）

更新内容: 復元の意味を「特定の日のデータを入れ直す」から「テーブル全体を特定の日の状態に戻す」に改めた。 退避は、日ごとの差分にする。

要点だけ読む場合

  • 課題: スナップショットは 120 時間しか持たず、それより前には戻せない。
  • 退避: 日ごとの差分を、Athena の UNLOAD で S3 に Parquet として出す。
  • 復元: 日付 D を指定する。全行を DELETE し、D までの退避データを INSERT する。テーブルは D 時点の状態になる。
  • 範囲: 手動実行のみ。日次の自動実行は作らない。
  • 追加物: テンプレート1つと、SQL 2ファイル。既存のテンプレートは変更しない。
  • 未確認: S3 Tables を元にした UNLOAD が動くか。再実行で行が重複するか。条件なしの DELETE が使えるか。実機で確かめる。

1. 目的とスコープ

スナップショットの保持期間より前の状態を、S3 Tables のテーブルに戻せるようにします。 保持期間を延ばすとメタデータが肥大化するため、延ばしません。 成果物はブログ記事と templates/ のテンプレートです。運用向けの自動化は作りません。

用語

  • 退避: その日の event_time の行だけを、日ごとの差分として Parquet に出力すること。
  • 特定の日への復元: 日付 D を指定して、テーブルの全行を D までの退避データで置き換えること。D より後の日付のデータは入らない。

含む

  • 退避先の S3 バケット、Athena ワークグループ、外部テーブル
  • 日ごとの差分を退避する UNLOAD の SQL
  • 特定の日へ復元する DELETE と INSERT の SQL
  • 検証手順と、記事への追記

含まない

  • 日次の自動実行。記事では方針の説明にとどめる
  • 毎日のテーブル全体のコピー
  • 既存の 2 つのテンプレートの変更
  • 退避データのライフサイクル管理

2. 前提と仮定

種類内容
あなたの指示 退避は Athena、形式は Parquet、粒度は日ごとの差分。復元は「特定の日に復元」で、テーブル全体を D 時点の状態に戻す。復元まで検証する。実行は手動。event_time のミリ秒未満の切り捨ては、バックアップとして不十分なので認めない。マイクロ秒まで残す。
私の仮定 差分の単位は event_time の日単位。復元は「全行を削除し、dt が D 以下の退避データを入れ直す」形。復元も Athena の SQL だけで行う。

3. 公式ドキュメントで確認した内容

  • Athena は S3 Tables に対して INSERT、UPDATE、DELETE、MERGE を実行できる。
  • ワークグループの暗号化が SSE-KMS または CSE-KMS だと、S3 Tables への書き込みはできない。Requester Pays が有効でも DML はできない。このワークグループは SSE-S3 にする。
  • UNLOAD の出力先は、パーティション指定がなければ空でなければならない。データがあると書き込まずに終わる。
  • パーティション指定がある場合は、同じ出力先と同じパーティションへの再実行が許される。
  • partitioned_by の列は、SELECT の最後に置く。Parquet の既定の圧縮は gzip。

参照元: UNLOAD / S3 Tables と Athena / Iceberg のデータ更新

4. 実機で確かめること

ドキュメントだけでは確定できません。検証で確認し、結果を記事に書きます。

#確認事項ダメだった場合
1 S3 Tables のテーブルを SELECT 元にした UNLOAD が動くか。ドキュメントに記載がない。 設計を見直す。代替は CREATE TABLE AS SELECT で外部テーブルに書く方法。
2 同じ日を再実行したとき、上書きされるのか、ファイルが増えて行が重複するのか。 再退避の前に、対象日のフォルダを削除する手順を加える。
3 条件なしの DELETE で、S3 Tables のテーブルの全行を消せるか。 event_time が全期間に入る範囲条件で DELETE する。
4 全行の DELETE のあと INSERT した結果が、元と一致するか。タイムスタンプの精度も見る。 型の指定を直す。

4.5 検証で分かったこと

退避のステップで確認した内容です。

  1. 確認済みUNLOAD は S3 Tables のテーブルを元にして動く。ただし、タイムスタンプ列には制約がある。
  2. 制約Parquet 出力は、ミリ秒精度のタイムスタンプしか書けない。Iceberg の timestamp はマイクロ秒精度のため、そのまま出すと NOT_SUPPORTED エラーになる。
  3. 不採用timestamp(3) への変換は切り捨てになる。.123456 と .123567 は、どちらも .123 になる。バックアップとして不十分なので採用しない。
  4. 採用event_time は文字列で退避する。CAST(event_time AS varchar) で 2026-10-01 00:00:00.123456 の形になる。復元で CAST(... AS timestamp(6)) を使うと、マイクロ秒まで戻る。Athena で往復を確認した。
  5. 注意同じ日を再実行すると、ファイルが増えて行が重複する。上書きにはならない。再退避の前に、その日のフォルダを削除する。
  6. 注意出力ファイルに拡張子は付かない。中身は Parquet である。

復元のステップで、次のことを確認しました。

  1. 確認済み条件なしの DELETE で、S3 Tables のテーブルの全行を削除できる。
  2. 確認済み2 つのカタログをまたいだ INSERT ... SELECT が動く。S3 Tables のカタログへの INSERT で、通常のカタログの外部テーブルを読める。テーブル名は、カタログ名から書く。
  3. 確認済み文字列の event_time が、timestamp(6) に正しく戻る。復元後のテーブルは、10/2 の状態の 2 行になった。
  4. 注意MSCK REPAIR TABLE は、データソースを AwsDataCatalog にして実行する。S3 Tables のカタログのままだと、「Unsupported DDL query for S3 table buckets」で拒否される。
  5. 確認済みDELETE と INSERT は、それぞれスナップショットとして残る。復元の操作も、スナップショットで巻き戻せる。

5. 構成

新しいテンプレート templates/athena-parquet-backup.yaml を作ります。

リソース役割
S3 バケット退避データとクエリ結果の置き場。暗号化は SSE-S3、パブリックアクセスはブロックする。
Athena ワークグループ結果の出力先を、上のバケットの別プレフィックスに固定する。暗号化は SSE-S3。
Glue データベースと外部テーブル退避した Parquet を読む。dt を文字列のパーティション列にする。event_time は、退避が文字列なので string で定義する。
Lake Formation の権限テンプレートでは付与しない。このアカウントでは、新しい Glue データベースに IAM_ALLOWED_PRINCIPALS の権限が自動で付く。同じ権限を作ろうとして AlreadyExists で失敗したため、外した。

退避先のレイアウト

s3://<バケット>/backup/sample_events/dt=2026-10-01/*.parquet
s3://<バケット>/backup/sample_events/dt=2026-10-02/*.parquet
s3://<バケット>/athena-results/

SQL ファイル

記事と実ファイルを一致させるため、templates/athena/ に置きます。

  • export_day.sql: 日ごとの差分の退避。partitioned_by = ARRAY['dt'] を指定する。
  • restore_to_date.sql: 特定の日への復元。全行を DELETE し、外部テーブルの dt が D 以下の行を INSERT する。INSERT では、文字列の event_time を timestamp(6) に戻す。

パーティションは MSCK REPAIR TABLE で読み込みます。パーティション射影は使いません。仕組みを増やさず、記事を読みやすくするためです。

6. データの流れ

退避（日ごとに実行）

1再退避の場合は、対象日のフォルダ dt=YYYY-MM-DD/ を先に削除する
2対象日を event_time の範囲で絞った SELECT を作る。event_time は文字列にする
3dt 列を最後に付けて UNLOAD する
4dt=YYYY-MM-DD/ に Parquet が出力される

復元（日付 D を指定）

1MSCK REPAIR TABLE でパーティションを読み込む
2退避済みの dt の一覧を確認する。D までの日が揃っているか見る
3dt が D 以下の行数を確認する
4S3 Tables のテーブルの全行を DELETE
5外部テーブルの dt が D 以下の行を INSERT
6元のテーブルの行を確認する
SQL のイメージ（実装時に確定） 
-- 退避（10/1 の例）
UNLOAD (
  SELECT event_id,
         CAST(event_time AS varchar) AS event_time,
         message,
         CAST(date(event_time) AS varchar) AS dt
  FROM "s3tablescatalog/s3tables-backup-demo"."backup_demo"."sample_events"
  WHERE event_time >= TIMESTAMP '2026-10-01 00:00:00'
    AND event_time <  TIMESTAMP '2026-10-02 00:00:00'
)
TO 's3://<バケット>/backup/sample_events/'
WITH (format = 'PARQUET', compression = 'SNAPPY',
      partitioned_by = ARRAY['dt']);

-- 復元（10/2 の状態に戻す例）
-- 事前確認
MSCK REPAIR TABLE "backup_demo_archive"."sample_events_archive";
SELECT dt, count(*) FROM "backup_demo_archive"."sample_events_archive"
WHERE dt <= '2026-10-02' GROUP BY dt ORDER BY dt;

-- 全行を削除
DELETE FROM "s3tablescatalog/s3tables-backup-demo"."backup_demo"."sample_events";

-- D 以下の退避データを入れ直す
INSERT INTO "s3tablescatalog/s3tables-backup-demo"."backup_demo"."sample_events"
SELECT event_id, CAST(event_time AS timestamp(6)), message
FROM "backup_demo_archive"."sample_events_archive"
WHERE dt <= '2026-10-02';

7. エラーと制約

記事にも書く内容です。

  • 注意復元の DELETE と INSERT は別の文。間で失敗すると、テーブルが空になる。INSERT を再実行すれば戻る。実行前に、手順 2 と 3 で退避データが揃っているか確認する。
  • 注意退避の漏れは、復元しても気づけない。D までの日のどれかが退避されていないと、その日の行が静かに欠ける。手順 2 の一覧で確認する。
  • 制約退避は event_time ベースの差分。退避済みの日の行を後から更新または削除しても、退避データには反映されない。その日を再退避しないと、D 時点の状態を正確に再現できない。
  • 注意退避は、その日が終わってから行う。日の途中に退避すると、残りの行が漏れる。
  • 注意同じ日を再実行すると、ファイルが増えて行が重複する。再退避の前に、対象日のフォルダを削除する。
  • 注意UNLOAD は、失敗時に出力済みデータを削除しない。再実行の前に、対象日のフォルダを確認する。
  • 注意退避データの event_time は文字列である。退避データを直接調べるときは、CAST が必要になる。
  • 問題なしUNLOAD のパーティション数の上限は 100。1 回の退避は 1 日分なので超えない。

8. 検証手順

現在のテーブルは、10/1 から 10/3 の 3 行です。

  1. テンプレートをデプロイする。
  2. 10/1 から 10/3 を 1 日ずつ退避し、S3 のフォルダと Parquet を確認する。
  3. 外部テーブルで、退避データを SELECT して確認する。
  4. 誤ったデータとして、evt-0004 を 10/3 に追加する。テーブルは 4 行になる。
  5. 10/2 を指定して、restore_to_date.sql を実行する。
  6. テーブルが evt-0001 と evt-0002 の 2 行になり、evt-0003 と evt-0004 が消えていることを確認する。

5 日待たずに検証するため、誤ったデータは INSERT で再現します。 退避データがスナップショットに依存しないことは、設計上の性質として記事に書きます。 5 日経過後の実証は、今回は行いません。
