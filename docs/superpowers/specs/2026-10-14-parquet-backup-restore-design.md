# Parquet 退避と特定の日への復元 設計

## 目的

スナップショットの保持期間（`maxSnapshotAgeHours` の 120 時間）より前の状態を、S3 Tables のテーブルに戻せるようにする。
保持期間を延ばすとメタデータが肥大化するため、延ばさない。
代わりに、日ごとの差分を Athena で S3 に Parquet として退避する。
復元では、日付 D を指定して、テーブル全体を D 時点の状態に戻す。

成果物は、ブログ記事と `templates/` のテンプレートである。検証が目的で、運用向けの自動化は作らない。

## 用語

- **退避**: その日の `event_time` の行だけを、日ごとの差分として Parquet に出力すること。
- **特定の日への復元**: 日付 D を指定して、テーブルの全行を、D までの退避データで置き換えること。D より後の日付のデータは入らない。

## スコープ

含むもの:

- 退避先の S3 バケット、Athena ワークグループ、退避データを読む外部テーブルのテンプレート
- 日ごとの差分を退避する `UNLOAD` の SQL
- 特定の日へ復元する `DELETE` と `INSERT` の SQL
- 検証手順と、記事への追記

含まないもの:

- 日次の自動実行（EventBridge Scheduler など）。記事では方針の説明にとどめる。
- 毎日のテーブル全体のコピー。差分のみを退避する。
- 既存の `s3tables-basic.yaml` と `glue-rollback-job.yaml` の変更
- 退避データのライフサイクル管理

## 前提と仮定

あなたの指示:

- 退避は Athena、形式は Parquet、粒度は日ごと。
- 退避は日ごとの差分にする。
- 復元は「特定の日に復元」。テーブル全体を D 時点の状態に戻す。
- 退避したデータからの復元まで検証する。
- 実行は手動。
- `event_time` のミリ秒未満の切り捨ては、バックアップとして不十分なので認めない。マイクロ秒まで残す。

私の仮定:

- 差分の単位は、テーブルのパーティションと同じ `event_time` の日単位とする。
- 復元は、全行を削除してから、`dt` が D 以下の退避データを入れ直す形にする。
- 復元も Athena の SQL だけで行う。

## 公式ドキュメントで確認した内容

- Athena は S3 Tables に対して `INSERT`、`UPDATE`、`DELETE`、`MERGE` を実行できる。
- ただし、ワークグループの暗号化が SSE-KMS または CSE-KMS の場合、S3 Tables への書き込みはできない。Requester Pays が有効な場合も DML はできない。このワークグループは SSE-S3 にする。
- `UNLOAD` の出力先は、パーティション指定がなければ空でなければならない。データがあると書き込まずに終わる。
- パーティション指定がある場合は、同じ出力先と同じパーティションへの再実行が許される。
- `partitioned_by` の列は、`SELECT` の最後に置く。Parquet の既定の圧縮は gzip である。

参照元:

- https://docs.aws.amazon.com/athena/latest/ug/unload.html
- https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables-integrating-athena.html
- https://docs.aws.amazon.com/athena/latest/ug/querying-iceberg-updating-iceberg-table-data.html

## 実機で確かめること

ドキュメントだけでは確定できない。検証で確認し、結果を記事に書く。

1. S3 Tables のテーブルを `SELECT` 元にした `UNLOAD` が動くか。ドキュメントに記載がない。
2. 同じ日を再実行したとき、既存ファイルが上書きされるのか、ファイルが増えて行が重複するのか。
3. 条件なしの `DELETE` で、S3 Tables のテーブルの全行を消せるか。
4. 全行の `DELETE` のあと `INSERT` した結果が、元と一致するか。タイムスタンプの精度も見る。

1 で動かない場合は、設計を見直す。代替は、`CREATE TABLE AS SELECT` で外部テーブルに書く方法である。
2 で重複する場合は、再退避の前に対象日のフォルダを削除する手順を加える。
3 で動かない場合は、`event_time` が全期間に入る範囲条件で `DELETE` する。

## 検証で分かったこと

退避のステップで、次のことを確認した。

1. **`UNLOAD` は S3 Tables のテーブルを元にして動く。** ただし、タイムスタンプ列には制約がある。
2. **Parquet 出力は、ミリ秒精度のタイムスタンプしか書けない。** Iceberg の `timestamp` はマイクロ秒精度のため、そのまま出すと `NOT_SUPPORTED` エラーになる。
3. **`timestamp(3)` への変換は切り捨てになる。** `.123456` と `.123567` は、どちらも `.123` になる。バックアップとして不十分なので採用しない。
4. **`event_time` は文字列で退避する。** `CAST(event_time AS varchar)` で `2026-10-01 00:00:00.123456` の形になる。復元で `CAST(... AS timestamp(6))` を使うと、マイクロ秒まで戻る。Athena で往復を確認した。
5. **同じ日を再実行すると、ファイルが増えて行が重複する。** 上書きにはならない。再退避の前に、その日のフォルダを削除する。
6. **出力ファイルに拡張子は付かない。** 中身は Parquet である。

復元のステップで、次のことを確認した。

7. **条件なしの `DELETE` で、S3 Tables のテーブルの全行を削除できる。**
8. **2 つのカタログをまたいだ `INSERT ... SELECT` が動く。** S3 Tables のカタログへの `INSERT` で、通常のカタログの外部テーブルを読める。テーブル名は、カタログ名から書く。
9. **文字列の `event_time` が、`timestamp(6)` に正しく戻る。** 復元後のテーブルは、10/2 の状態の 2 行になった。
10. **`MSCK REPAIR TABLE` は、データソースを `AwsDataCatalog` にして実行する。** S3 Tables のカタログのままだと、「Unsupported DDL query for S3 table buckets」で拒否される。
11. **`DELETE` と `INSERT` は、それぞれスナップショットとして残る。** 復元の操作も、スナップショットで巻き戻せる。

## 構成

新しいテンプレート `templates/athena-parquet-backup.yaml` を作る。

| リソース | 役割 |
|---|---|
| S3 バケット | 退避データとクエリ結果の置き場。暗号化は SSE-S3、パブリックアクセスはブロックする。 |
| Athena ワークグループ | 結果の出力先を上のバケットの別プレフィックスに固定する。暗号化は SSE-S3。 |
| Glue データベースと外部テーブル | 退避した Parquet を読む。`dt` を文字列のパーティション列にする。`event_time` は、退避が文字列なので `string` で定義する。 |
| Lake Formation の権限 | テンプレートでは付与しない。このアカウントでは、新しい Glue データベースに `IAM_ALLOWED_PRINCIPALS` の権限が自動で付く。同じ権限を作ろうとして `AlreadyExists` で失敗したため、外した。 |

退避先のレイアウトは次のとおり。

```
s3://<バケット>/backup/sample_events/dt=2026-10-01/*.parquet
s3://<バケット>/backup/sample_events/dt=2026-10-02/*.parquet
s3://<バケット>/athena-results/
```

SQL は、記事と実ファイルを一致させるため `templates/athena/` に置く。

- `export_day.sql` 日ごとの差分の退避。`UNLOAD` に `partitioned_by = ARRAY['dt']` を指定する。
- `restore_to_date.sql` 特定の日への復元。全行を `DELETE` し、外部テーブルの `dt` が D 以下の行を `INSERT` する。`INSERT` では、文字列の `event_time` を `timestamp(6)` に戻す。

外部テーブルのパーティションは、`MSCK REPAIR TABLE` で読み込む。パーティション射影は使わない。仕組みを増やさず、記事を読みやすくするため。

## データの流れ

退避:

1. 再退避の場合は、対象日のフォルダ `dt=YYYY-MM-DD/` を先に削除する。
2. 対象日を `event_time` の範囲で絞った `SELECT` を作る。`event_time` は文字列にする。
3. `dt` 列を最後に付けて `UNLOAD` する。
4. `dt=YYYY-MM-DD/` に Parquet が出力される。

復元（日付 D を指定）:

1. 外部テーブルで `MSCK REPAIR TABLE` を実行する。
2. 退避済みの `dt` の一覧を確認する。D までの日が揃っているか見る。
3. `dt` が D 以下の行数を確認する。
4. S3 Tables のテーブルの全行を `DELETE` する。
5. 外部テーブルの `dt` が D 以下の行を `INSERT` する。
6. 元のテーブルの行を確認する。

## エラーと制約

- 復元の `DELETE` と `INSERT` は、2つの文に分かれる。間で失敗すると、テーブルが空になる。この場合は `INSERT` を再実行すれば戻る。実行前に、手順 2 と 3 で退避データが揃っているか確認する。
- 退避の漏れは、復元しても気づけない。D までの日のどれかが退避されていないと、その日の行が静かに欠ける。手順 2 の一覧で確認する。
- 退避は `event_time` ベースの差分である。退避済みの日の行を後から更新または削除しても、退避データには反映されない。その日を再退避しないと、D 時点の状態を正確に再現できない。記事に制約として書く。
- 退避は、その日が終わってから行う。日の途中に退避すると、残りの行が漏れる。
- 同じ日を再実行すると、ファイルが増えて行が重複する。再退避の前に、対象日のフォルダを削除する。
- `UNLOAD` は、失敗時に出力済みデータを削除しない。再実行の前に、対象日のフォルダを確認する。
- 退避データの `event_time` は文字列である。退避データを直接調べるときは、`CAST` が必要になる。
- `UNLOAD` のパーティション数の上限は 100 である。1回の退避は 1 日分なので問題ない。

## 検証手順

現在のテーブルは、10/1 から 10/3 の 3 行である。

1. テンプレートをデプロイする。
2. 10/1 から 10/3 を 1 日ずつ退避し、S3 のフォルダと Parquet を確認する。
3. 外部テーブルで、退避データを `SELECT` して確認する。
4. 誤ったデータとして、`evt-0004` を 10/3 に追加する。テーブルは 4 行になる。
5. 10/2 を指定して、`restore_to_date.sql` を実行する。
6. テーブルが `evt-0001` と `evt-0002` の 2 行になり、`evt-0003` と `evt-0004` が消えていることを確認する。

5 日待たずに検証するため、誤ったデータは `INSERT` で再現する。
退避データがスナップショットに依存しないことは、設計上の性質として記事に書く。5 日経過後の実証は、今回は行わない。
